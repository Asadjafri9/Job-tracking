# M5 evidence — daily source monitoring and notifications

Scope implemented and verified on the loopback stack only. No live career
page, ATS endpoint, or provider call was fetched; the fetch boundary is
proven with injected transports/resolvers and the pipeline with fake
fetchers against the real local PostgreSQL.

## MON-001 — sources, preferences, schedule API/UI

- `apps/api/app/modules/monitoring.py`: `/monitored-sources` CRUD under
  owner-scoped RLS. Hard cap of five non-deleted sources (409 beyond).
  URLs are validated through the same `validate_public_url` boundary used
  by the fetcher (https only, port 443, no userinfo, no IP literals);
  timezones must be IANA names.
- Sources save without consent but remain `PAUSED`/`setup_required`
  until `scheduled_check_consent` is given; consent stamps
  `consent_revision = revision`, so any schedule/region/timezone edit
  stales consent and clears `next_run_at` until re-confirmed
  (`_activation_fields`). Saved-key consent requires scheduled consent
  (mirrors the DB check constraint).
- `PATCH` is revision-checked (`expected_revision` → 409); `pause`/`resume`
  actions recompute `next_run_at` via `next_daily_run_utc` (09:00 local,
  DST-safe) only when consent is current. `DELETE` marks the source
  DELETED, clears `next_run_at`, and cancels queued runs — no scheduled
  work survives removal.
- Monitoring preferences are confirmed `ProfileFact` rows with the
  `MONITORING` purpose (PROF-001), matched deterministically in the scan
  pipeline — no private/contact data leaves the service for matching.

## MON-002 — safe fetch and extraction boundary

- `apps/api/app/monitoring/fetch.py`: `validate_public_url` rejects
  non-https schemes, credentials in URLs, IP literals (incl. IPv6 and
  mapped forms), and non-443 ports. `resolve_public_addresses` requires
  every A/AAAA answer to be globally routable; any private/loopback/
  link-local/multicast/reserved answer fails closed (rebinding guard).
  The connection is pinned to the validated address (`https://<ip>`) with
  the real host sent via `Host` header and TLS SNI — hostname verification
  is preserved.
- Redirects (max 3) are revalidated per hop: scheme/host/DNS re-checked,
  and cross-host redirects re-run the robots check. 304 honours stored
  etags; 401/403 → `FetchDenied`; 429 carries the Retry-After hint;
  5xx → `FetchFailed`; other codes → `FetchUnsupported`. Responses are
  byte-bounded at 2 MiB with a 30 s deadline; the same host is throttled
  to one request per 2 s.
- `robots.txt` is fetched once per host per run (24 h cache) and evaluated
  by RFC 9309 substring matching over the union of all matching groups —
  a disallow never loses a longest-pattern tie (conservative).
- `apps/api/app/monitoring/extract.py`: JobPosting JSON-LD (`@graph`,
  `itemListElement`, `hasPart` traversal; TELECOMMUTE → remote), RSS and
  Atom items, then a bounded HTML anchor fallback that keeps only
  job-shaped links resolved to https. Candidates capped at 200, titles at
  255 chars, evidence anchors recorded per candidate. Unparseable input
  returns empty — nothing is invented.

## MON-003 — due scheduler, run dedupe, match pipeline

- `apps/api/app/worker/scheduler.py` (from M1/JOB-001, extended): unique
  `(source_id, scheduled_local_date)` daily runs, restart catch-up limited
  to one missed slot inside 6 h, older slots recorded `SKIPPED` —
  verified by 18 dispatch tests.
- `apps/api/app/worker/handlers.py`: the scan handler revalidates run
  state, source state, schedule, and consent revision at claim time
  (stale → `CANCELED`), performs the bounded fetch **outside** the
  owner transaction, then re-locks and applies the outcome in a second
  transaction — provider/network work never extends a DB transaction.
  MANUAL runs validate separately (source not deleted, revision match).
- `apps/api/app/monitoring/scan.py`: job identity is a native external id
  or the canonical public URL (tracking params stripped); title/employer
  are review hints. Meaningful-field changes bump `meaningful_revision`
  and emit an `UPDATED` notification; identical re-scans change nothing.
  Jobs are never closed after one scan — closure requires absence from
  two consecutive COMPLETE successful scans (last_seen_at behind the
  previous complete run's start).
- Matching is deterministic keyword matching against MONITORING-purpose
  confirmed facts; `match_reason` records the rule hits (or that no
  preferences were configured). No AI matching is wired yet — discovered
  jobs stay visible regardless, which is the contract's outage behaviour
  by construction.

## MON-004 — notifications, badge, job links, run UI

- `Notification.event_key` = `{job_id}:{event}:r{meaningful_revision}` —
  exact dedupe via the existing unique constraint and insert-conflict
  no-op, so replays and repeated scans never duplicate.
- `GET /notifications` (+ `unread` filter and `unread_count`),
  `POST /notifications/{id}/read`, `POST /notifications/read-all`;
  `GET /monitoring-runs`, `GET/PATCH /discovered-jobs` (save/dismiss/
  reopen; CLOSED jobs can only be reopened).
- `apps/web/src/ui/alerts.tsx`: source add form with explicit consent
  checkboxes and IANA timezone picker, per-source state/next-run/
  last-success/last-error/setup-required, check-now/pause/resume/
  consent/remove actions, discovered-job list with save/dismiss/reopen
  and external posting links, notifications with read/read-all, and a
  recent-checks run history with FAILED/PARTIAL honesty. Discovered jobs
  are never applications.
- `App.tsx`: the header bell is now a live link to Job alerts showing the
  unread count badge, refreshed on navigation and every 60 s.

## Review findings (fixed before push)

Codex review (`gpt-6-luna` high — `sol6.1` is not enabled on the account)
found three real issues, all fixed and covered by regression tests:

- Duplicate postings on one page could violate job-identity uniques and
  leave a run stuck in RUNNING — candidates are now deduped per scan on
  both identity surfaces, and updates never steal another row's URL.
- A source deleted mid-fetch could still have results persisted — the
  apply phase now revalidates source state and revision and records the
  run CANCELED when stale.
- `response.content` buffered bodies before the 2 MiB check — both
  robots and content reads now stream and abort at the bound.

## Known limits (not claimed)

- ATS-specific endpoint adapters are not implemented; HTML/JSON-LD/
  RSS/Atom extraction is the supported surface. `source_kind` is stored
  for honesty but unsupported kinds fall back to the same extractors.
- AI-assisted matching (MON-003's changed-text AI path) is not wired;
  deterministic matching runs unconditionally and `match_reason` says so.
- No real DNS/TLS fetch against a live career page has been performed;
  only injected transports on the loopback stack.
